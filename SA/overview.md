VLA 流程：

最近的潮流是把大型语言模型 （LLM） 和视觉语言模型 （VLM）的语义功能**融合进原来视觉为主的端到端大模型中**，所以出现了各种VLA（vision-language-action）模型。

这些VLA模型直接从视觉到action，所以都是端到端大模型，而非三段式的经典自动驾驶方案。**action可以是车辆运动轨迹，也可以是具体的控制指令**。

OpenDriveVLA 利用开源预先训练的语言基础模型，根据 3D 环境感知、自我车辆状态和驾驶员命令生成驾驶动作。

- 数据预处理

  数据预处理部分是把三维感知信息变为二维信息（2D feature）并放置到BEV鸟瞰图中。比如，三维感知到一位行人，他/她的身高胖瘦这些三维信息是无用的，只有他的二维坐标是有用的，这个二维坐标就是这个目标的2D feature。

  核心架构中反复出现三个概念map，scene和agent，解释如下：

  - map（地图）：在模型里主要指驾驶场景中的静态地图元素。Map QueryTransformer 模块会从鸟瞰视图（BEV）特征中提取这些静态结构信息，**像车道边界、可行驶区域等，生成的地图token，编码了如车道拓扑、道路边界等信息**。这些信息为车辆规划可靠的行驶轨迹提供了基础，让模型能理解道路的结构和规则，从而做出合理决策。
  - scene（场景）：代表整个驾驶场景的环境上下文。Global Scene Sampler 模块基于多视图 2D 特征，编码周围驾驶场景的上下文信息，产生场景令token。这个 token 捕获了全局 2D 环境上下文，包含了**驾驶场景中各种物体的整体布局、环境状况等信息**，帮助模型从宏观角度理解所处的驾驶环境，在规划轨迹时考虑场景整体情况。
  - agent（主体 / 智能体）：指驾驶场景中的动态物体，即**除了自车之外的其他活动元素，包括其他车辆、行人等**。Agent QueryTransformer 模块负责检测和跟踪场景中的这些动态主体，提取以主体为中心的token，模型通过对这些主体令牌的处理，**预测它们的未来运动，理解主体间的动态交互，在规划自车轨迹时避免碰撞，确保行驶安全**。

  和上面三个要素对应的：

  Global Scene Sampler 对来自多视图 2D 特征的周围驾驶场景上下文进行编码，生成场景标记。

  Agent QueryTransformer 检测并跟踪场景中的动态 Agent，提取以 Agent 为中心的token，Na表示检测到的 Agent 数量。

  Map QueryTransformer 提取静态结构信息，例如车道边界和可驾驶区域，形成地图token。

  三者合一，通过以视觉为中心的感知任务，包括 3D 检测、跟踪和分割，视觉编码器生成结构化的环境token，以空间为基础的方式捕获动态代理行为和静态地图结构。**输出标记表示为 env =（scene, agent , map)环境三元组，用作后续阶段的视觉环境表示**。

- 多模态数据对齐技术

  为了弥合提取的视觉标记和预训练 LLM 的词嵌入空间之间的模态差距，这篇论文采用了分层视觉-语言特征对齐策略。

  为了从3D 视觉感知模块中提取的视觉标记，这篇论文引入了三个特定于标记的投影器projector。scene,agent,map前面三个要素每一个都有自己的projector。

  projector的作用就是“对齐”，**把scene,agent,map的多模态信息对齐到language space（LLM能使用的语言空间），而对齐的方式就是映射mapping**。把一种模态的信息从原始模态空间映射到另外一个模态的空间，这是神经网络的拿手好戏。

  所以可以合情推理，projector就是一种模态转换的神经网络，作为整个openDriveVLA的组件存在。

- 驾驶指令调优

  为了将高水平的驾驶知识嵌入到 OpenDriveVLA 中并提高其推理能力，这篇论文在培训期间引入了专门的驾驶指导调整阶段，也就是微调。不是在推理时执行显式思维链 （CoT） 推理，这会显着增加延迟，而是**通过监督指令调整将基本的驾驶知识提炼到模型中**，以实现推理速度和推理效率之间的权衡。

  在调优过程中，使用精选的驾驶指令的问答数据集将语言领域的驾驶知识注入到模型中。该数据集涵盖了广泛的与驾驶相关的推理，包括感知理解、运动预测、注意力分配、动作推理和高级决策。通过对这组不同的驾驶查询进行培训，OpenDriveVLA 学会了将驾驶场景置于上下文中，遵循命令，并生成基于语义和行为的规划决策。

- agent 环境自我交互（预测每个目标的运动轨迹）

  自动驾驶中可靠的轨迹规划需要基于空间的环境 3D 表示。除了感知之外，它还必须理解自我载体与周围主体agent之间的动态互动。有效的交互建模对于确保在实际驾驶约束下规划的轨迹既可行又无碰撞至关重要。周围主体agent有一些是会动的，需要预测它们的轨迹。

- 端到端轨迹规划

  在轨迹生成阶段，OpenDriveVLA 将未来的驾驶作规划为接下来几秒钟内的一系列航点，。每个航点代表自车在时间步 t 的2D坐标。为了使LLM启用自回归生成（也就是根据前面已经生成的内容“牵引”出后面要生成的），首先将航点标记化为离散文本标记序列： traj = Tokenizer (ego) 。然后将生成过程转换为因果序列预测任务，其中每个标记都以视觉感知标记Venv 、自我状态Sego和驾驶命令Xdri 为条件进行预测。

MindVLA：

关键技术包括如下：

- 3D 高斯表示：采用能够承载丰富语义，且具备出色多粒度、多尺度 3D 几何表达能力的 3D 高斯作为中间表征，利用海量数据进行自监督训练，提升下游任务性能。
- 通过训练，模型能够自己切换快慢系统；
- Diffusion 轨迹优化：利用 Diffusion 将动作词元解码成优化的轨迹，通过自车行为生成和他车轨迹预测的联合建模提升在复杂交通环境中的博弈能力，可根据外部条件动态调整生成结果；

- 智驾芯片的门槛，以及对智驾算法的影响；

  我了解的，国内的智驾芯片（除了华为），只有算力单元，ISP 等少数 IP 是自研的，其他的如 CPU，GPU, DSP 等，都是购买 ARM,Synopsys, Cadence 等 IP 设计公司成熟的方案。所以这些大家都差不多，影响性能的大都在自研 IP 上。

  目前看到，算法的门槛在于算力单元，算力单元直接影响智驾算法的运行效率；以及系统能够达到的 DDR 带宽，PCIe/以太网的带宽，这决定了芯片内部，芯片间的数据交换能力，是系统的瓶颈。

  算力方面，小鹏/理想的算力单元都是用的自研的 IP，没有采用 NV 的 cuda 架构，这就导致上层的智驾模型需要重新部署，虽然硬件设计的算力很高（MAC 阵列数 n * NPU 峰值频率 * 4（每个 NPC 有 4 个 NPU） * 2 （每个 DLA 有 2 个 NPC）），但是你软件生态没人家好，重新部署后，生产的可执行文件在指令级别就没人家高效。另一方面定点的算力不是瓶颈，难在浮点的算力上，你的硬件设计能力没有 NV 强，导致在浮点计算上无法通过堆算力的方式来追上人家，所以需要用到浮点计算的模型，在图灵芯片运行效率就不行。

  举个例子，就好比我之前在龙芯做的事情一样，龙芯设计的架构和 Intel 的 X86 架构不一样，你一个软件虽然都是用 C 语言写的，但是你得用龙芯的编译器重新编译成龙芯架构能够识别的文件格式，然后去执行。

  带宽方面，虽然大家都是采购别人家的 DDR，以及内部的总线，但是你的芯片能不能达到理论的带宽上限，是跟你的芯片设计能力有关的。比如说，由于经验问题，我们可能没有意识到 ACPU 会和 ISP 发生带宽抢占，导致 ISP 跑不动设计帧率，自然就影响智驾算法的运行。

  对智驾算法的影响，上面就是很典型的影响。总结一下，虽然设计算力有那么多，但是软件生态加上芯片设计问题，导致智驾算法没有跑在 NV 芯片上效率高。所以芯片团队需要回归到 GPGPU 的方向（初代由于没经验，采用稳妥方案，设计采用简单一点的 NPU 架构），大模型团队需要去优化算子，匹配底层的硬件。
